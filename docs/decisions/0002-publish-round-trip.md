# 2. Publish round trip, and what it proved

**Status:** Spike completed, 17 August 2026
**Context:** Step 4 of the build order in `cross-platform-delivery-plan.md`

The delivery model assumes we can stage an app, seed it, install it, publish an
update and have it apply. Everything downstream of that assumption was being
built on top of it before anyone had watched it work. This records the run.

## What was done

Against Pear CLI 3.2.0, using `apps/supervisor` and a throwaway link:

```
pear touch                          -> pear://os5tpk…gr1o
pear stage <link> apps/supervisor   -> version 134, 133 files
pear seed --no-tty <link>           -> announced, discovery + content key published
pear dump <link> <tmp>              -> 133 files retrieved
# bump version, then
pear stage <link> apps/supervisor   -> version 135, diff was one file
pear dump --force <link> <tmp>      -> one file updated in place, 0.1.0 -> 0.1.1
```

## What it proved

Staging produces a versioned drive and **updates are incremental**. Changing one
file moved the drive from 134 to 135 and transferred that file alone, both on
stage and on dump. That is the property the whole update story depends on, and
it holds.

Seeding announces correctly: the drive key, discovery key and content key are all
published, NAT type was detected, and the seeder picked up the new version while
running without needing a restart.

Applying an update to an existing copy is a diff, not a re-download. The dumped
directory went from 0.1.0 to 0.1.1 with one file rewritten and the other 132
untouched.

## What it did not prove

**Nothing crossed the network.** The seeder reported `0 peers, upload 0B` for the
entire run. Both dumps read from the local Pear sidecar's storage, because the
sidecar is a per-machine singleton and there is no `PEAR_DIR` equivalent to
isolate a second instance on one host.

So this validated the staging, versioning and diff mechanics, not peer-to-peer
retrieval. **A second machine is required** to close that gap, and it should be
done before anyone relies on the update path. It is cheap — one other host, one
`pear dump` — but it cannot be faked locally.

## What it changed

`pear stage` does not read `.gitignore`. The first dry run was about to publish
`out/win32-x64/lcai-supervisor.exe` at 57.6 MB, plus the `bare-build` toolchain
and its icon assets, into a drive that every user replicates. The upstream
template ships no `pear.stage.ignore`, so anyone following it inherits this.

`apps/supervisor/package.json` now carries an explicit ignore list, which took
the staged app from 188 files to 133 and removed the binary entirely. Anything
added under `apps/` should have its staged contents checked with
`pear stage --dry-run` before a first release, because the failure is silent and
expensive rather than loud.

The `upgrade` link no longer points at the upstream template's link, which was
somebody else's application. It is a development link generated by `pear touch`
whose secret key exists only on one developer machine. **A production release
needs its own link under the multisig policy**; this one must not ship.

## Follow-ups

1. Repeat the dump from a second machine and confirm transfer over the network.
2. Decide the production link and its multisig quorum, then regenerate. See
   `pear multisig` and open decision 5 in the delivery plan.
3. Seeding must be always-on for a release to be installable. A release nobody
   seeds is a release nobody can install, and right now nothing seeds.
