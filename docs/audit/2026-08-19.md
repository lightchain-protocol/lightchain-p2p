# Full application audit

Date: 2026-08-19
Method: thirteen specialist agents run as read-only investigations in two waves,
each carrying its own brief from `.cursor/agents/`, each required to verify by
running rather than by reading. Findings triaged centrally; the critical ones
fixed in this pass and re-verified. Scope: 299 tracked source files, 19
packages, 3 applications, CI, packaging and the release path.

Predecessor: [audit-2026-08-18.md](../audit-2026-08-18.md), whose every finding
is settled below.

---

## Verdict

**Yesterday's audit found no critical or high-severity findings in first-party
code. This one found four, and they were all introduced by the last two
commits.** That is not a reversal of the earlier judgement — it is what happens
when 11,600 lines of wallet, bridge, price and guard code land in a day, on a
red pipeline, with no second reviewer.

The four, in the order they matter:

1. **Every prompt sent to the inference service ran over TLS that verified no
   certificates.** `packages/inference` pinned `bare-fetch: ^1.2.4`, and
   `bare-tls` did not load a trust store or reject an untrusted certificate
   until 3.0.0. pnpm satisfied the mismatch by nesting a second network stack
   under that one package — the package carrying prompts to the consumer API and
   reading back the public key each prompt is sealed to. Any attacker on the
   path could read every prompt, substitute their own key, and name themselves
   the delegate a deposit authorises. **No compromised renderer required.** This
   was the only finding in the audit reachable by an ordinary network attacker,
   and it is the one nobody was looking for.

2. **The operating-system confirmation before a large transfer was forgeable by
   the renderer.** The confirmation reply travelled as a plain control line on
   the same pipe the window writes requests to, the id counted up from one, and
   the main process broadcast each request to every window before drawing the
   dialog. A window could read the id and answer its own dialog. Two agents
   found this independently and both demonstrated it against the running
   application; a third reproduced it in isolation against the real module.
   Worse, the harness carried a check named _"there is no handler for forging a
   confirmation"_ which passed the whole time — the forgery is not a handler.

3. **`ai.fund` moved any amount out of the wallet with no password and no
   dialog**, and the same call raises a delegate's allowance by the amount
   deposited, with nothing anywhere lowering it again. So an unguarded `ai.fund`
   granted standing spending authority rather than spending once.
   `bridge.approve` was unguarded too and could mint an unbounded ERC-20
   allowance to the bridge router.

4. **Opening Send from any zero-balance holding silently retargeted the
   transfer.** The asset picker offered only assets with a balance, so arriving
   from an empty row left it with no selection — and `Number('')` is `0`, so
   every consumer aimed at `holdings[0]`, which sorts to LCAI on Lightchain.
   Clicking Send on a WETH-on-Arbitrum row asked the worker to build 1 LCAI on
   chain 9200.

Beneath those, three guards were found to be **configured and inert**: the
`pearBoundary` import rule matched no file in the repository, three CI checks
compared generated files against themselves, and the last pushed commit was red
at `pnpm format:check`, so lint, typecheck, 968 tests, eight structural checks
and four chain surveys never ran on the commit that introduced all of the above.

All four criticals are fixed and verified. The tree is green.

### What is genuinely strong

Worth saying plainly, because the list above is not the whole picture and a
report that only enumerates faults misrepresents the codebase.

The fork-safety property holds and was proved rather than assumed:
`entryAction` decides on facts that cannot change, `apply` never consults the
parser, and a twelve-case matrix plus a two-peer replication test confirm a
build that has never heard of an event kind reaches the same view as one that
has. Author signatures bind the room key and cannot be lifted between rooms. The
chain-id replay guard is enforced on every one of the seven signing paths. No
floating point appears anywhere near an amount, a fee, a balance or a price —
traced end to end from a typed string to a signed transaction. Per-token
decimals are right on all six chains, verified against sixteen live contracts
including the USDT-is-18-on-BSC trap. The rule that a failed read is never
rendered as zero is genuinely enforced, not merely stated. `packages/blind`
carries a matched positive and negative control that is the strongest single
piece of evidence in the repository. And the price layer's licensing analysis —
reading a `view` function accepts no terms and tells no third party which tokens
somebody holds — is the best-argued decision in the tree.

## What was fixed in this audit

Eleven changes. Each is listed with the command whose output settled it.

### 1. Unverified TLS on the inference path — CRITICAL

`packages/inference/package.json`

The pin moves from `^1.2.4` to `^3.2.0`, with the reason recorded in a top-level
`//bare-fetch` note so the next person meets it before the temptation.
`pnpm install` removed 95 packages: the entire nested stack —
`bare-fetch@1.6.0`, `bare-http1@3.8.2`, `bare-https@1.3.0`, `bare-tcp@1.9.1`,
`bare-dns@1.0.5` and `bare-tls@1.2.1`.

```
Packages: +2 -95
3.1.8      node_modules\bare-tls        <- one stack, and it verifies
3.2.0      node_modules\bare-fetch
```

Because this class of fault produces no error and no symptom — both versions
install, both resolve, both work — a new check enforces it:

```
$ node scripts/check-runtime-majors.mjs
12 bare-* modules, each asked for at one major
```

and, with the old pin restored to prove it can fail:

```
bare-fetch is asked for at 2 different majors:
      v1: packages/prices (^1.2.4)
      v3: apps/chat (^3.2.0), packages/chain (^3.2.0), packages/host (^3.2.0), …
```

It is wired into CI beside the other eight structural checks.

### 2. The forgeable confirmation — CRITICAL

`apps/chat/electron/main.js`, `apps/chat/workers/guard.mjs`

Three changes, and all three are needed. Any one alone leaves a way in.

- **The renderer can no longer write a control line.** `writableByRenderer`
  refuses any payload that is not a newline-delimited run of JSON envelopes,
  which is all `request()` has ever sent. Main keeps the monopoly on
  `wallet:confirmed`.
- **A confirmation request is no longer forwarded to any window.**
  `watchForConfirmRequests` now returns the bytes that are safe to broadcast and
  withholds its own. The renderer discarded those lines anyway, so nothing
  visible is lost; what is gained is that the id is not something a window has
  seen.
- **The id is sixteen random bytes** rather than a counter, so it cannot be
  guessed either.

### 3. `ai.fund` and `ai.withdraw` unguarded — CRITICAL

`apps/chat/workers/handlers/ai.mjs`

Both now go through `guard.allow`, with the dialog text built from the
transaction the worker assembled rather than the request that asked for it. The
`ai.fund` dialog names the delegate the deposit authorises, because that is the
part that outlives the transfer.

### 4. `bridge.approve` unguarded and unbounded — HIGH

`apps/chat/workers/handlers/bridge.mjs`

Two ceilings, because the existing re-quote is not one. `quoteTransfer` echoes
back the amount it was asked about, so the "route's answer, not the window's"
reasoning did not hold — it was the window's number laundered through an
`eth_call`. Verified against the live mainnet router: asking about `2^256-1`
returns `2^256-1`.

- The approval may not exceed what the address actually holds. An allowance
  beyond the balance grants authority over funds that do not exist yet, which is
  the whole hazard.
- The approval goes to the operating system like every other write. It is
  arguably the more consequential of the two: a transfer moves what was named
  once, an allowance stands until something revokes it, and nothing here does.

The router is a `TransparentUpgradeableProxy` whose ProxyAdmin and owner are the
same externally-owned account. Nothing in the current implementation lets a
third party spend the allowance, so this was a loaded gun rather than a fired
one — which is why it is graded HIGH and not CRITICAL. It is now unloaded.

### 5. `keysDir` and `containerName` were renderer-writable — MEDIUM/HIGH

`apps/chat/workers/handlers/settings.mjs`, and the two Settings inputs

Both are arguments handed to Docker, not settings. `keysDir` becomes the source
of a `-v <dir>:/data` bind mount into a container running as root;
`containerName` becomes the subject of `docker logs` — another container's
credentials, returned to the window — and `docker rm -f`. Neither needs an
attack on Docker; both are ordinary Docker doing what the argument says.

They are out of the allowlist. The two inputs are now `readonly` with a hint
saying where to change them, rather than left live and silently failing — a
control that lies about what it does is its own defect.

### 6. One malformed write wedged the data plane — HIGH

`apps/chat/electron/main.js`

`writeWorkerIPC` passed anything to `pipe.write`. `framed-stream` maps only
strings to buffers, so a number reached `_frame(data.byteLength)` as `undefined`
and threw a tick later, _after_ `write` had already returned `true`. Every
subsequent request then hung forever, with the worker alive, the status line
reading "connected", and nothing anywhere reporting an error — the silent-drop
failure this codebase treats as the worst class of bug. The same type check
closes it, plus a 160 MB ceiling so the worker's reader cannot be grown without
bound by a window writing endlessly with no newline.

### 7. A non-additive change that dropped whole messages — CRITICAL (permanence)

`packages/protocol/src/message.ts`

When streaming added `frames`, `ciphertext` went from required to optional. A
build compiled before that change meets the new shape, throws inside
`parseAnswer`, and the throw propagates through `parseEntry` — so
`isValidEntry` is false and `room.messages()` drops **the entire message**, text
and all, shown nowhere. The `frames` docstring promised the opposite.

`parseAnswer` now has the same asymmetry `parseEvent` already had: a malformed
answer in a known shape is still rejected, and an answer in a shape this build
has never heard of drops the claim and keeps the message. The permanence rule is
documented at the change site. A regression test writes an answer quoted in a
third, invented shape and asserts the text survives while the claim does not:

```
$ pnpm --filter @lcai-p2p/room test
Tests  113 passed (113)
```

This is the one fix that would have become unfixable at release.

### 8. The portfolio chart reported a fabricated gain — HIGH (money)

`packages/prices/src/history.ts`

`portfolioAcross` plotted a grid point when _any_ holding was priced there, and
summed only that subset. Feeds write at wildly different rates, so their sampled
windows do not line up: a portfolio of 1 ETH and 2000 USDC drew a line that
began at the USDC alone and stepped up when the ETH series started. Measured
against the live feeds, that was **+113.51% over a week in which neither asset
moved** — reported as complete.

A sum is not a chart of one asset. A missing term does not make the total
uncertain, it makes it wrong, and wrong in the direction that looks like news. A
point is now plotted only where every contributing holding is priced; a holding
with no price anywhere is excluded from that requirement and still counted in
`unpriced`. A new `trimmed` count lets the worker say the line starts later than
the range asked for.

The existing test asserted the old behaviour — the bug written down as expected
— and is corrected. A second test reproduces the original shape with both prices
held perfectly flat and asserts the answer is zero change.

### 9. Send aimed at the wrong asset on the wrong chain — CRITICAL (money)

`apps/chat/renderer/lib/assets.js`

Two changes. `chosenAsset()` now treats the empty string as nothing rather than
letting `Number('')` resolve to `holdings[0]`. And the picker offers every
holding rather than only those with a balance — hiding them was tidier and worse
in both directions: somebody looking for ETH they no longer hold found it simply
absent with nothing saying why, and arriving from a zero-balance row left no
selection at all. The review step already refuses an amount beyond the balance
and says so in words, which is a better answer than a missing row.

Verified against the running application, on the exact case that was reported:

```
row clicked      : WETH on Arbitrum One, see activity
asset page shows : Wrapped Ether WETH on Arbitrum One 0 WETH $0.00 Receive Send
send dialog aims : {"chosen":"WETH on Arbitrum One — 0","balance":"0 WETH on Arbitrum One"}
```

Before: `assets.quoteSend` with `chainId: 9200`, `amount: 1000000000000000000`,
review reading "1 LCAI" and "Lightchain (chain 9200)".

### 10. The portfolio chart drew one range and lit another — MEDIUM

`apps/chat/renderer/lib/asset-detail.js`

Both range strips wear `.asset-range`, and this module queried it unscoped, so
it reset the Portfolio card's buttons as well as its own. The Portfolio kept
requesting whatever range it was actually on while lighting whichever one the
asset page had just set — a year of data under a control reading 1W, with
nothing else on the card naming the range. Both queries are now scoped to
`#asset-ranges`.

### 11. Sub-cent network totals rounded to zero — MEDIUM (money display)

`apps/chat/renderer/lib/assets.js`

A hand copy of the worker's `formatUsd` that had already drifted: without the
sub-cent branch a tile holding $0.0013 read `$0.00` beside a row, formatted by
the worker, reading $0.0013. LCAI trades near a tenth of a cent, so a wallet
holding only LCAI showed six networks worth nothing next to a total that was
not. The copy is now faithful, and says so.

### 12. The import boundary rule matched no file in the repository — HIGH

`packages/eslint-config/index.js`, and both app configs

Rule 1 of three — applications never import Pear modules directly — is described
in README and CONTRIBUTING as "enforced by lint, not convention". It was not
enforced anywhere. Flat-config `files` patterns resolve against the directory
holding the config, and each app runs `eslint .` from its own directory, so an
`apps/**` glob inside `apps/chat` matched nothing. Confirmed the way a change
here must be confirmed, since a green lint run is what the defect produces:

```
before   renderer  no-restricted-imports: undefined
         worker    no-restricted-imports: undefined
after    chat renderer : ACTIVE
         chat main     : ACTIVE
         chat worker   : off        <- the documented exception
         testkit src   : off        <- packages are where the stack belongs
```

The glob is now package-relative, and the rule moved out of the default export
into a new `appConfig`. That split is the real fix: sharing one config between
apps and packages is _why_ the rule had to carry an `apps/**` glob, and the glob
is what made it inert. When it first fired it correctly flagged
`packages/testkit` for building a Corestore — which is that package's entire
job. The two are now separate statements.

### 13. CI was red, and formatting was withholding everything behind it

35 tracked files failed `prettier --check`, and `Format` is step two of the
`check` job. On `b6dc274` — the commit that added the six-chain wallet, the
bridge, the guard and `packages/prices` — lint, typecheck, 968 tests, all eight
structural checks and all four chain surveys were skipped. `pnpm install
--frozen-lockfile` is the only thing that ran.

`pnpm format` fixes it. Whether a whitespace failure should be able to withhold
sixteen substantive checks is a workflow question recorded below as O2.

## New findings, not fixed

Triage was: fix security holes, fork risks, money bugs and non-additive schema
changes; write up the rest. What follows is the rest, worst first.

### High

**R1 — an attachment bounds block count, not bytes.**
`packages/room/src/attachments.ts:296-315`. `get()` checks `size` against
`MAX_ATTACHMENT_SIZE` and `blockLength` against `MAX_BLOCKS`, and never checks
`blob.byteLength`, which `parseEntry` also leaves unbounded. `MAX_BLOCKS` is
derived on a one-kilobyte-per-block floor, but hyperblobs writes 64 KiB blocks —
so a message declaring `size: 5` with `blockLength: 25600` makes a fetching peer
download roughly 1.6 GiB and `b4a.concat` it into one buffer before the length
check runs. Peak memory is about double that, which kills the Bare worker. Fix:
bound `byteLength` in the same pre-fetch block, and derive `MAX_BLOCKS` from the
real block size so the two bounds agree.

**R2 — any 64-hex string in a message opens a persistent Hypercore.**
`packages/room/src/attachments.ts:345-360` accepts any well-formed hex key with
no check that it belongs to a writer in the room, `store.get({ key })` persists
it, and `#remote` has no bound and no eviction. The renderer supplies the
trigger: it auto-fetches on the sender's declared `type`. N messages with random
core keys means N cores on disk, N live sessions and N hanging fetches on every
other member's machine, restarted on each re-render. Fix: bound `#remote` with
LRU eviction, pass `createIfMissing: false` for keys not seen in a signed entry,
and remember failures in the renderer so a re-render does not refire.

**R5 — nothing bounds the size of an entry a member can commit.** A consequence
of the fork fix rather than a flaw in it: `apply` must append on structure
alone, so a member appending `{ type: 'x', junk: '<100 MB>' }` directly to their
writer core gets it signed, replicated to everyone, and written into a log that
cannot be pruned. The only fork-safe bound is the encoded byte length of the
block itself, which every peer computes identically. **This needs a decision
before release, not a fix now** — `MAX_ENTRY_BYTES` is permanent once chosen,
because raising it later is itself a fork.

**D1 — the seeder's DHT identity is random on every launch.** `apps/seeder`
constructs `new Hyperswarm()` with no `keyPair`, so `blind-peering` connects
under a fresh key each time and the blind peer downgrades every registration to
`announce: false`. The release is stored and never advertised — the one thing
registering is supposed to prevent. This is the exact bug the ROADMAP records as
found and fixed; it was fixed in `apps/chat` and not here. The seeder also never
prints its own key, so an operator cannot add it to a trusted list. **This is on
the critical path**: standing up a seeder per `docs/availability.md` today
produces a false green.

**D2 — registration cannot report failure.** `addCores` is a one-way Protomux
message with no reply channel, and `addCore` resolves on `peer.connecting`. So
registration has three outcomes and reports one: accepted resolves, downgraded
also resolves, unreachable never settles. `lodgingFailures` — the only
availability alarm in the system — is therefore dead in both real failure modes,
and its test injects a rejection this code path cannot produce.

**W1 — the keystore password is on the `docker` command line.** See M5 above.
`--env-file` closes the unprivileged-user half today.

**P2 — the v2 preimage is computed over different objects when signing and
verifying.** Signing passes the entry as constructed; verifying passes the
output of `parseEntry`, which rebuilds from a fixed key list and discards the
rest. Any field the parser drops turns an honest signature into "unverified
author", and `resolveRoom` then stops honouring that author's edits and
withdrawals. Not reachable today — every producer happens to build exactly the
parser's field set — and nothing enforces that. Fires on the first optional
field added to `ChatMessage`.

**P3 — `BEYOND_V1` reintroduces the enumeration v2 exists to remove.** The v1
fallback is offered when none of four named fields is present, so a field added
and not added to that list is both unsigned and accepted: a v1-signed message
with a new field bolted on still attributes to its original author. Structurally
a signature-scheme downgrade decided by the entry's own unauthenticated fields.
Not exploitable today; the list happens to be complete. Fix: derive the guard
from the canonical key set rather than maintaining a list.

**A2 — three CI "is it current" checks cannot fail.** The Build step runs
`pnpm build`, which regenerates `renderer/index.html` and
`renderer/partials/sprite.html`; the `--check` steps that follow then compare
each file against what the build just wrote. A hand-edited `index.html` gets a
green run and is silently reverted on the next local build. Fix: split
`generate` from `build` so CI never regenerates a tracked artefact — noting the
asymmetry that `renderer/tokens.css` is gitignored and _must_ still be generated
in CI.

**O1 — the release workflow as written has never run.** Three runs of
`build-matrix`, all on 17 August. The `signing` job, the macOS notarization step
and the entire `desktop` job were added on 18 August and have executed zero
times. README and ROADMAP both state that CI builds a DMG, an MSIX and an
AppImage per tag; it has never built one, and there are no tags. Separately, the
`desktop` job **does not smoke test** — the binary matrix executes what it built
and the installer jobs do not, which inverts the priority.

**O5 — on the recommended signing route, binaries ship unsigned and the log says
otherwise.** `check-signing.mjs:21` treats `WINDOWS_CERT_SHA1` and
`WINDOWS_SIGN_HOOK` as interchangeable for "Authenticode signature on the
supervisor and seeder binaries". Only the first is consumed by the binary
matrix; the second is the MSIX maker. Azure Artifact Signing — the route
`docs/signing-procurement.md` recommends — cannot produce a thumbprint. So the
one job whose purpose is to tell the truth about signing would state the
opposite of it.

**O8 — `apps/chat` has no `pear.stage.ignore`.** Both other apps have one, with
`purge: true`, on the authority of ADR 0002 — which records nearly publishing a
57 MB binary into a drive every user replicates. `apps/chat` was added after
that ADR and did not get the treatment, and it is by far the worst case: its
`out/` holds the packaged Electron app plus three installers, and its
devDependencies include Electron itself. The failure is silent and permanent.

**Q1 — a harness check asserted the forgery was impossible.**
`locking-check.mjs:193-198` tries `wallet.confirm` as a _request name_, gets
"unknown request", and reports `PASS  there is no handler for forging a
confirmation`. The forgery is not a handler. That check is worse than absent: it
is the reason nobody looked. Now covered properly by the thirteen new cases
above, but the misleading check should be reworded or removed.

**Q3 — the CI harness loop aborts and cannot go red.** `set -e` inside a `for`
loop means one flaky harness stops the rest, and `continue-on-error: true` on
the job means the run stays green. On the last push, `clipboard-check` failed
environmentally (`xclip` cannot reach the display `xvfb-run --auto-servernum`
allocated for the app) and six harnesses — roughly 155 checks — never ran, with
nothing reporting it. Fix: collect exit codes instead of aborting, wrap the whole
block in one `xvfb-run --server-num=99`, then remove `continue-on-error`.

**S4 — neither workflow declares `permissions:`.** Both inherit the repository
default, which is **write** on contents, actions, packages, deployments and
security events. `actions/checkout` runs with `persist-credentials: true`, so
that token is written into `.git/config` in a workspace where `pnpm build`,
`pnpm test` and eleven `node scripts/*.mjs` then execute. `main` has no branch
protection. The `onlyBuiltDependencies` allowlist closes the easiest path
(install scripts) and not build-time or test-time execution. Fix: `permissions:
contents: read` and `persist-credentials: false`; three lines, no behaviour
change.

## Checked and sound

Recorded so the next reader knows what was examined and found correct.

**Protocol and rooms.** `entryAction` reads the compiled function, not the
comment: no reference to any parser. A twelve-case matrix confirms the verdict
never depends on comprehension — an unknown event kind, an unknown entry type, a
future `v` and an unparseable message all append; only a non-object or an
unusable writer key is skipped. `apply` appends the raw block. Four tests write
entries this build cannot read, including a two-peer replication case. The room
key is genuinely in the signature preimage and a signature is refused in another
room. Key order does not change the preimage. Version refusals are legible.
`ModelRef` travels as key _and_ version everywhere it is stored or compared.
Invites are spent exactly once, carry no room key, and only a writer may issue
one. `removeWriter` announces before it commands — the opposite of `addWriter`,
and correct, because removing can cost the remover the ability to say so.
Attachments are encrypted at rest and in flight, with the storage directory
scanned under a positive control so an empty scan cannot read as success.
Nothing believes the sender about what a file is: `sniff` reads magic bytes and
excludes SVG.

**Money.** No floating point on any path from a typed amount to a signed
transaction — `toBaseUnits` is string arithmetic that refuses extra places and
grouping separators rather than rounding, and everything after is `bigint`.
Decimals verified against sixteen live contracts. A price cannot influence an
amount: token sends always confirm rather than deriving a threshold from a feed,
which is the right call and the reason a manipulated pool read cannot lower a
safety threshold. Failure is not rendered as zero anywhere reachable — an
unreachable chain yields `{ held: [], error }` with `complete: false`, a locked
wallet yields `null`, and history reports `source: 'none'` with a sentence
rather than an empty list. Chain identity is pinned from configuration on all
seven signing paths. Keys stay in the worker: the unlocked wallet holds a
derived account, not the phrase, and no `console.*` in any package touches key
material. Bridge recipient encoding is left-padded correctly and verified
against the deployed routers. `RpcPool` deliberately keeps `sendRawTransaction`
out of the retry path — a pool that retried a broadcast would double-send.

**The shell.** `require`, `process`, `module` and `Buffer` are all undefined in
the renderer; the CSP is `default-src 'self'` with no network origin and an
`https` fetch is blocked; navigation is closed in both directions; permissions
are deny-by-default. `settings.write` refuses a literal `__proto__` delivered as
raw JSON. The handler table has a null prototype. `rid`/`t` are reserved and a
caller passing either throws. Every path through `onLine` replies, including a
payload that will not serialise. `chooseFiles` lets the renderer lower a ceiling
and never raise it. `safeFileName` strips path separators, control characters,
Windows reserved names and the bidi overrides that matter, with 30 unit tests.

**Data plane.** The two-machine tests prove what they claim: the latecomer is
created after the publisher goes offline, with its own Corestore in its own
directory, and reads bytes it cannot have had. `packages/blind` runs a real
`blind-peer` server and its two tests are a matched pair — metadata-only
registration fails to deliver the bytes while the full one succeeds. The
testkit negative control is strict, matched on the error message, and unmodified
since the day it was written.

**Supply chain.** `pnpm audit --prod`: no known vulnerabilities, 403 packages.
`onlyBuiltDependencies` is a three-name allowlist with a stated reason for each
— the best supply-chain control in the repository. `pnpm.overrides` pins `tar`
and `tmp` forward with the reasoning recorded. All four install steps use
`--frozen-lockfile`. No untrusted input reaches any `run:` block in either
workflow: zero matches for `github.event`, `head_ref` or `inputs.`.

**Craft.** `scripts/notarize-macos.mjs` is the best-built script here —
credentials checked inside the script rather than in an `if:`, a clean skip
off-darwin, packing with `ditto` because `notarytool` will not accept a bare
executable, and declining to staple a lone executable while explaining why that
is still fine. ADR 0002 has a "What it did not prove" section more useful than
the rest of the document. `docs/install.md` opens with "There is no release
yet." That habit is why this audit could be done from the repository at all.

## Recommended order

**Before anything else.** Push. The tree is green here and `main` is red, one
commit behind, and both documents claim otherwise.

1. **Close the two remaining renderer-reachable gaps** — `bridge.acknowledge`
   (E11) and the request timeout (E7) — and reword the `locking-check` assertion
   that claimed the forgery was impossible (Q1).
2. **Make CI able to fail.** Collect harness exit codes instead of aborting
   (Q3), fix `xclip` under `xvfb`, set `permissions: contents: read` and
   `persist-credentials: false` (S4), then remove `continue-on-error`. Split
   `generate` from `build` so the three tautological checks become real (A2).
   None of this is more than an afternoon and all of it is load-bearing.
3. **Fix the seeder before standing one up** (D1, D2, D3). The ROADMAP's next
   action is "one blind peer and one seeder", and doing it today produces a
   process whose registration is never announced, that cannot tell you it
   failed, and that stops serving the current release the first time you stage a
   new one. All three are invisible from its own status output.
4. **Decide `MAX_ENTRY_BYTES`** (R5) and fix the two attachment bounds (R1, R2).
   The first is permanent once chosen and can only be decided before publication.
5. **Correct the documents** — but only after CI is green, or the corrections
   become claims nothing backs. Every number should be reproducible from a
   command pasted beside it.
6. **Add `pear.stage.ignore` to `apps/chat`** (O8) and regenerate its upgrade
   link (L5), before any tag. Both are silent and permanent after the fact.
7. **Settle the legal entity name.** It is one decision that fixes the MSIX
   Publisher CN permanently _and_ becomes the Apple seller name, and it blocks
   certificate procurement, which has the longest external lead time of
   anything here.

### Still needing a human decision

- The legal entity name, and custody of two separate key sets (the signing
  certificate and the release multisig). ADR 0005 leaves custody deliberately
  unproposed.
- Whether this repository goes public or the organisation moves to Team.
  Branch protection is impossible on the current plan, so CODEOWNERS is
  advisory and every CI run is a post-hoc report on a commit that already
  landed. Fixing the placeholder handles will not change that.
- A host for one blind peer and one seeder. About $5 a month on a 2 vCPU VPS
  with a public address. Until one exists, a room is available only while a
  participant has the app open, and a release is installable only while the
  staging laptop is awake.
- ADR 0005, still _Proposed_. A tag today would build a Snap and a Flatpak the
  ADR says not to ship, both of which silently remove peer-to-peer updates.

## Method note

Thirteen agents, two waves, each seeded with its own brief from
`.cursor/agents/` and told the same four things: report rather than change, so
one person holds the whole picture; verify by running, because a finding without
a command and its output is an observation; cite `file:line` with a severity and
a concrete failure; and say what you checked and found sound, because a clean
area is a result.

The waves were sequenced so the second could be pointed at what the first found.
That mattered: the security auditor was handed four claims to adjudicate rather
than asked to look for them, and it confirmed three at the reported severity,
downgraded one, and then found something worse that nobody had been looking for
(S1). Two agents independently found the confirmation forgery from different
directions, which is the strongest signal in the report — and a third, given it
as a claim, refused to take it on trust and reproduced it in isolation.

One agent's finding was corrected by another: the claim that a warm Turbo cache
could produce a green CI run that wrote nothing is true locally and false in CI,
because there is no persisted cache and every guard is duplicated as its own
step. That correction is recorded rather than dropped, because a false alarm
noted is worth more than one quietly deleted.
