# Security, functionality and platform audit

Date: 2026-08-18
Scope: the whole repository — 18 packages, 3 applications, CI, packaging and
scripts, ~24,000 lines of first-party code. Method: line-by-line review of the
security-critical paths (wallet, crypto, chain, rooms, inference, IPC, Electron
shell, Docker orchestration), mechanical verification (tests, typecheck, lint,
format), dependency audit, and packaging review.

**Verdict up front: no critical or high-severity findings in first-party code.**
The codebase is unusually careful — the threat model is written into the files,
and the claims in the documentation held up when checked. What follows are five
medium findings, a set of low ones, and the operational gaps that matter more
than any of them.

## Medium findings

### M1. The private key reaches `argv` at the Docker boundary

`packages/worker/src/commands.ts` — `importKey` builds
`docker run … --private-key <key> --password <password>`. The supervisor's
comment says the key "never reaches argv, an environment variable or a log,"
and that is true between the operator and the supervisor (it is read from
stdin). It is **not** true for the supervisor-to-Docker leg: the key sits in
the `docker` process's argument list, visible in the host's process table for
the duration of the run, and in the container's `Config.Cmd` while it exists
(`--rm` bounds this).

Single-user machine, brief window — but the documented guarantee is broken at
exactly the point the documentation says is protected.

**Fix:** pass the key on the container's stdin (`docker run -i …`, with the
binary reading stdin as it already does for the supervisor) or via a
`mktemp`-created file bind-mounted read-only and deleted after. Either keeps
the stdin-only promise end to end.

### M2. `sendTransaction` trusts the node's `chainId`

`packages/chain/src/send.ts` fetches `chainId` from the RPC node and signs
with it. The network profiles in `packages/worker/src/network.ts` pin the
expected values (mainnet 9200, testnet 8200) — they are displayed in Settings
— but nothing **enforces** them before signing. A hijacked RPC endpoint (DNS,
TLS termination upstream, or a malicious custom endpoint) could answer with a
foreign chain id and obtain a signature replayable on another EVM chain where
the same key holds funds.

**Fix:** one comparison in the chat worker (or in `sendTransaction` via an
`expectedChainId` option): refuse to sign when `rpc.chainId()` disagrees with
the profile. A wrong answer is already a fatal error everywhere else in this
codebase; this is the one place it is believed.

### M3. SIWE sign-in signs whatever the service sends

`packages/inference/src/api.ts` — `signIn` signs the challenge message the
consumer API composes, without parsing it and without showing it to the user.
That is standard for SIWE, but it means a compromised or malicious consumer
API can obtain an EIP-191 signature over **any** text — a login challenge for
a different service, an off-chain authorization, anything `personal_sign`
verifies against.

**Fix:** parse the SIWE message before signing and check `domain`, `uri` and
`chain-id` against the expected service, and surface the message in the UI
("the service asked you to sign this"). Both are cheap; the first is the one
that cannot be talked around.

### M4. The renderer can start an arbitrary worker file

`apps/chat/electron/main.js` — `pear:startWorker` passes the
renderer-supplied specifier straight to `require.resolve('..' + specifier)`.
There is one legitimate worker; anything else reachable by path traversal
(`/../../…`) would be executed as a Bare worker with full data-plane access —
the wallet, the rooms, the keys. Exploitation requires a compromised renderer
first, and the renderer is sandboxed and text-only (see strengths below), so
this is defence in depth rather than a live hole.

**Fix:** an allowlist of one: `if (specifier !== '/workers/main.mjs') return false`.

### M5. Keystore password at rest and in `docker inspect`

Two halves of the known interim position, recorded so the audit trail shows
they were seen:

- `apps/chat` `settings.json` can hold `workerPassword` in cleartext (mode
  0600 where the OS honours it; nothing on Windows). The ROADMAP already calls
  an environment variable "an interim position, not the end state" — the
  settings file is the same position in a different place.
- `runWorker` passes it as `-e WORKER_KEYSTORE_PASSWORD=…`, which is readable
  for the container's whole lifetime via `docker inspect`. Docker access is
  root-equivalent on most hosts, which bounds the impact, but a secret that
  outlives the command that carried it is worth a follow-up (Docker supports
  `--env-file`; a 0600 file in `keysDir` is strictly better than container
  metadata).

## Low findings and observations

- **L1 — Electron itself carries a high-severity advisory** (sandboxed iframe
  `allow-popups` bypass) and the Forge tree has 19 more (tar, tmp,
  extract-zip, image-size, app-builder-lib). None reach production: the app
  loads no remote content and no iframes, and the rest are build-time tools
  that are never shipped. Bump Electron anyway; it is the one package here
  that _is_ the user's runtime.
- **L2 — No per-transaction confirmation at the worker layer.** While the
  wallet is unlocked, `wallet.send`, `ai.fund` and `ai.withdraw` sign whatever
  amount the renderer passes, with no ceiling and no password re-entry. That
  is ordinary hot-wallet posture and the UI confirms, but the worker is the
  trust boundary and it currently trusts the renderer completely. A
  `confirm:` round-trip or a per-session spending cap would harden it.
- **L3 — No memory hygiene for key material.** Derived keys and the phrase are
  plain JS strings/buffers that are never zeroed. Mostly a platform
  limitation; `Uint8Array.fill(0)` on the scrypt outputs and session keys at
  `close()` is available and free.
- **L4 — CODEOWNERS still names `@track-a` / `@track-b`.** Branch protection
  cannot be enabled, which is a process exposure, not a code one. The default
  `* @lightchain-protocol/p2p` line at least routes everything somewhere.
- **L5 — The upgrade link in `apps/chat/package.json` is a development link**
  whose secret key sits on one machine. Documented in place and in the
  ROADMAP's open decisions; listed so the audit says it out loud: a
  production release under this link puts OTA updates behind a single
  machine's key.
- **L6 — Rooms: any writer can add a writer.** There is no admin concept;
  membership is permissionless among members. That is a legitimate design for
  a chat room, but it should be a stated decision (one line in
  `packages/room`'s README), because people will assume otherwise.
- **L7 — Author signatures do not cover `event`, `answer` or `replyTo`.**
  Checked and satisfied this is sound: entries live in per-writer signed
  cores so they cannot be altered after the fact, `answer` is verified against
  the _worker's_ signature rather than the relayer's, and every event's `text`
  (which is covered) restates what happened. Worth a comment in
  `authorPreimage` so nobody "fixes" it by adding fields and forking the
  format.

## Things checked that are **not** problems

So the record shows they were looked at:

- Keystore/vault crypto: encrypt-then-MAC, `timingSafeEqual`, scrypt N=2^18,
  KDF parameter bounds on decrypt (a hostile file claiming N=2 or N=2^30 is
  rejected), identical errors for wrong-password vs tampered-file, and
  verify-before-write on create/import/changePassword. Correct and careful.
- Renderer XSS: message text is built from DOM text nodes only; no
  `innerHTML` anywhere; links are `<span role="link">` that ask the main
  process to open them, and `openExternal` refuses anything that is not
  http/https. A chat room cannot inject markup.
- Deep links: a clicked `lightchain://` invite opens a **prefilled dialog**,
  it does not join. Following a link is never enough to enter a room.
- Electron hardening: `sandbox: true`, `nodeIntegration: false`,
  `contextIsolation: true`, single-instance lock (a second window onto one
  Corestore would deadlock — handled).
- Worker IPC: the renderer receives an address and lock state; private keys
  never cross; the phrase crosses only when the user asks, once.
  `worker.status` returns named fields rather than the config precisely so
  the password cannot ride along.
- Docker invocation: `spawn` with argument vectors, no shell anywhere;
  `display` strings redact secrets so logging the wrong variable cannot leak.
- Inference: every relayed frame is verified against the assigned worker's
  signature **before decryption**, using the same preimage the contract's
  `disputeResponseMismatch` checks; commitment to chain is checked after the
  fact and a mismatch is disputable (and the fee returns).
- Session-key wrapping: fresh ephemeral P-256 pair per recipient, matching the
  deployed Go workers byte for byte.
- Rooms: additive-only schema discipline, malformed entries skipped rather
  than wedging `apply`, the view appends raw values so parser drift cannot
  fork the room, and the sealed room registry migrated from plaintext with
  the old file deleted.
- Hyperswarm DHT key persistence: the app builds its own DHT with a persisted
  key — the upstream behaviour (silently discarding `keyPair`) was found and
  worked around, with a comment that will save the next team a week.

## Functionality findings

- **F1 — Deep-link scheme bug in `forge.config.js`.** `protocols: [{ …,
schemes: [pkg.name] }]` registers `@lcai-p2p/chat`, which is not a legal URL
  scheme — `electron/main.js` knows this and registers `lightchain` at
  runtime, which covers Windows and Linux, but on **macOS** the scheme comes
  from the packaged Info.plist, so packaged Mac builds would register a broken
  scheme and invite links would not open the app. One-word fix:
  `schemes: ['lightchain']`.
- **F2 — Documentation drift** (carried over from the earlier review):
  README's status table still says `apps/chat` and `packages/chain` are "Not
  started"; ROADMAP's "Smaller pieces" still lists a broadcast transaction as
  undone above the section documenting the mined one. Neither is code, both
  will mislead a new reader.
- **F3 — `docs/spikes/` does not exist.** The plan defines a spike as done
  only when its answer is written down there; the answers live in the ROADMAP
  instead. Either create the folder or amend the plan's definition of done.

## Platform findings

- The build matrix is the right shape: six native runners for the Bare
  binaries (each **executes** what it built, after signing, because signing
  rewrites the file), three for the Electron installers, and
  `check-signing.mjs` announcing at the top of every release build what will
  and will not be signed — which closes the "unsigned looks identical to
  signed" trap.
- Flatpak and Snap are configured but undecided, correctly: neither can
  receive peer-to-peer updates. ADR 0005 (MSIX + signed `.exe`, AppImage
  only) is proposed and dated today — it needs a decision, and it is the
  decision that determines whether Linux users get updates at all.
- Everything ships unsigned until procurement lands. That is the correct
  interim state and it is announced honestly by `docs/install.md`.
- **Not code, but the largest exposure in the audit:** availability still
  depends on participant laptops. No blind peer and no seeder is running, so
  rooms and releases both die when everyone closes the app. The code gap is
  closed and tested (`packages/blind`, `packages/seed`); the machine gap is
  not. Likewise the second-machine verification of the publish round trip.

## Dependency and supply-chain notes

- Production tree: clean audit, and the dependency set is small and mostly
  first-party Holepunch modules that are mirrored locally in this workspace —
  which is itself a mitigation worth keeping.
- The crypto is `@noble/curves`, `@noble/hashes`, `@scure/bip39`,
  `@scure/bip32` — audited, pure-JS, and pinned by lockfile. The choice is
  forced (libsodium has no P-256) and documented.
- The 20 advisories are all reachable only through Electron Forge and its
  packaging chain. They run on CI runners and developer machines, so they are
  not nothing — a malicious tarball processed by `@electron/rebuild` is a
  developer-machine compromise — but they do not ship.

## Recommended order

1. F1 (one word), M4 (one line), M2 (one comparison) — an afternoon, all three.
2. M1 — stdin to the container, keeping the promise the docs already make.
3. M3 — validate the SIWE message before signing.
4. Decide ADR 0005, replace CODEOWNERS placeholders, enable branch protection.
5. Stand up one blind peer and one seeder; verify the round trip from a second
   machine.
6. L2/L3 hardening when the wallet UI next changes.
