Roadmap

What is not built yet, and which kind of not-built each one is. Nothing here has a date.

What the statuses mean

Not started
No code has been written. Nothing outside the work is holding it up.
Built, nothing runs it
The code exists and is tested. Nobody operates it, so the property it provides is not there.
Waiting on procurement
Finished as far as this repository goes. What is missing has to be bought.
Not decided
A choice has to be made before any of it is work.
Decided against, for now
Looked at, turned down, and written up with the condition that would change the answer.

Built, nothing runs it Blind peers, so a room outlives everyone leaving

A room replicates only while somebody holding it is online, so two people who are never online at the same time exchange nothing. A blind peer closes that: a machine that holds an encrypted room without being able to read a word of it.

The code is finished. A room is lodged with the blind peers named in Settings as it opens, and packages/room has a test that shuts down every participant and reads the room back on a machine that was never given the keys. It has been done through the running application as well, not only in a test.

Waiting on
A machine. There is no public fleet, and a third-party peer will cache for us without serving on our behalf.
Recorded in
docs/availability.md, which has the systemd units.

Built, nothing runs it A seeder that stays online

Updates arrive peer to peer rather than from a download server, which means somebody has to be holding the release. apps/seeder does exactly that and is verified holding a real Pear-staged release. Applications are client-only by default, so until a seeder runs somewhere continuously a release reaches nobody once the machine that staged it goes offline.

Waiting on
A host to run it on, continuously.
Recorded in
ROADMAP.md, under infrastructure to operate.

Waiting on procurement A signed release you can install

Nothing is published. Every tag builds a DMG, an MSIX and an AppImage alongside standalone binaries for six hosts, and every one of them is unsigned, uploaded as a build artifact and released nowhere. Building from source is the only way to run this today.

The signing and notarisation steps are written and skip themselves when no credentials are set, so the workflow will not change when certificates arrive. Until they do, macOS reports the app as damaged rather than as unsigned, and Windows warns on every download.

Waiting on
An Apple Developer certificate, whose D-U-N-S number takes up to five business days to issue and two more before Apple can see it; a Windows certificate; and a production upgrade link under a multisig quorum. The legal entity name chosen becomes the Windows Publisher name, and that is permanent once a signed release ships.
Not decided
Which Windows and Linux artifacts to ship. ADR 0005 proposes an MSIX with a signed executable beside it, and AppImage alone, on the grounds that an installation which cannot receive peer-to-peer updates stops receiving fixes invisibly. It needs a decision rather than more research.

Not started More than one conversation at a time

The worker holds one conversation, and starting a second closes the first. A session is expensive to open — a sortition draw takes the better part of a minute and creates a transaction — so it is made once and reused for every question after, which is right for one conversation and is the reason there is only one.

Recorded in
apps/chat/README.md, under what does not exist yet.

Not started Continuing an earlier conversation

Saved conversations are listed beside the models and can be read, and that is all they can be. Carrying on with one means paying for a new session, because the session that produced it was closed and the worker that answered was drawn for it. Nothing carries the earlier exchange into the new session either, so the model would not have read it.

Recorded in
apps/chat/README.md.

Not started Searching what a model said

Search covers room messages, across every room this peer holds. It does not cover conversations with a model: those are kept in a separate transcript log, encrypted under a key only this wallet can derive, and nothing reads it looking for anything.

Recorded in
apps/chat/README.md.

Not decided Reaching a worker directly

Every prompt goes through a foundation-operated relay and dispatcher today, the same path the web client uses. The alternative is for clients to find workers themselves over HyperDHT, addressed by the worker's registered key: fewer hops on the critical path, and streaming a token at a time becomes natural rather than something an intermediary has to relay frame by frame.

It is not scheduled, because it is not decided. Worker selection determines who earns, so doing it permissionlessly and fairly depends on verifiable randomness — and the audit in this repository records that selection is currently a SHA-256 draw carrying a note to upgrade it to a real one. What was asked for is a design and a testnet prototype returning with measurements, not a migration.

Waiting on
Verifiable randomness on the chain, and a vote. Neither has happened.
Recorded in
The proposal, section 9, and docs/proposals/AUDIT.md section 1.2.

Not started Data availability, packages/da

The package is named in CODEOWNERS so that ownership is settled before the code exists, and that is the whole of it: there is no such directory. What it becomes will have to clear the same bar the other replicating packages clear — a two-machine test with the publisher offline for part of the run — because an availability bug does not appear on one machine.

Recorded in
The status table in README.md, and CONTRIBUTING.md for the testing bar.

Decided against, for now iOS and Android

Deferred on purpose, and written down rather than left to drift. On iOS and Android the shell is a store binary and the store owns the update channel, so the one property this whole architecture is built for — publish a fix and have it reach people directly — does not exist there.

There is no working reference either: the pear-mobile counterpart the documentation mentions is not in the mirror, and PearPass, the reference implementation, does not use over-the-air updates on mobile at all. And an open model catalogue, where anyone can publish and any user can call any model, is a plausible store rejection that no amount of engineering retires.

What is deferred is delivery, not portability. The Bare worker is the same code a mobile worklet would run, so choosing this costs nothing structurally.

Recorded in
ADR 0001, accepted 17 August 2026.
Revisit when
Desktop has shipped a signed release and applied at least one over-the-air update in the field, and there is usage data showing demand.

Decided against, for now Hardware wallets

Investigated and turned down, and the transport was never the problem: WebHID works in this renderer under the sandbox and the content security policy, which was the part most likely to be impossible.

The reason not to build it is what the device would be asked to do. This application signs on every message, every rename and every writer grant, and a hardware wallet is built for a wallet that signs occasionally. Worse, it could not show what it was signing: a message commits to a hash of its text rather than to the text, deliberately, so that a newline cannot impersonate the field separators and claim a different author. The sentence being approved is the one field the reader cannot see, and no device can invert a hash to recover it. Shipping this would look like protection and would teach somebody to press Approve without reading.

Recorded in
ADR 0006, 18 August 2026.
Revisit when
packages/protocol grows a session key for some other reason. That is most of the four to six weeks this would take, and it is a wire format that can never be migrated once it ships.
